# Phengos premium desktop implementation plan

Prepared 2026-10-03 from the ten sheets in `New Design`, the live repository, `PHENGOS_ROADMAP.md`, `PHENGOS_FEATURE_INVENTORY.md`, and the upstream comparison in `PHENGOS_DESKTOP_FLOW_RESEARCH.md`. This is an implementation plan, not a claim that the catalog has been reached. Desktop/PC is first. Voice mode is explicitly outside these tasks; the design must leave room to connect voice later. The user is handling card backend work in another session: these tasks own display design, frontend interaction and utility integration, with no new card backend implementation.

## Diagnosis and design decisions

The v17 film, live circle, 21 preserved destinations, several canonical-data cards and guarded proposal approval path now exist locally. The catalog's interaction model is still missing: the menu is a bounded dialog rather than a coherent layered desktop workspace; most routed pages retain the previous visual system; static overview and adaptive cards are not yet one design; card controls differ by domain; and the assistant conversation is still largely a separate page. A 60 fps encoded film has been verified, but actual browser rendering has not been measured. These are the main reasons the current result feels far from the catalog.

**Design means the entire experience:** motion, animation, display, dashboard composition, aesthetics and user-oriented utility. A polished home image alone cannot pass any milestone. Each task must be reviewed as a desktop walkthrough showing what appears for a real user, why it appears, what action is available, how the interface moves between states, and how it looks at rest. The circle should feel curious and energetic during transitions, then settle when the user is reading or working. Motion should clarify hierarchy and causality; visual depth and asymmetry should support scan order and legibility.

The catalog suggests a sequence: **intro/idle circle → menu → general surface → domain → subcomponent → working surface**, with the circle becoming smaller and calmer at deeper layers (sheets 2–4 and 10). The general surface combines always-visible, trustworthy overview with time-sensitive cards (sheets 3, 5–6). Domain colors/icons share one language (sheet 8); red means urgent, not decoration (sheet 9). Cards need preview, adjust, approve, decline, completion and return states (sheet 6). Sheet 7's voice transport and listening/speaking UI remain future work.

Use the existing React Router, TanStack Query, Motion and domain APIs. Motion's [transform-based layout animations](https://motion.dev/docs/react-layout-animations) and Query's [mutation invalidation](https://tanstack.com/query/latest/docs/framework/react/guides/invalidations-from-mutations) fit the current architecture. [Adaptive Cards](https://github.com/microsoft/AdaptiveCards) and [React Grid Layout](https://github.com/react-grid-layout/react-grid-layout/blob/master/README.md) solve schema exchange and user-draggable widgets, respectively, but neither supplies the catalog choreography. [AG-UI](https://github.com/ag-ui-protocol/ag-ui) and [CopilotKit's approval pattern](https://github.com/CopilotKit/OpenGenerativeUI/blob/main/docs/human-in-the-loop.md) inform the later agent/voice boundary without replacing the working assistant transport now. A development-only scenario gallery can show complete catalog states while backend feeds are built separately; the production home must never present those examples as saved user data.

## Five implementation tasks

### 1. Build the real desktop workspace and layer navigation

**Scope:** Replace the home-only dialog feel with the catalog's persistent desktop shell. Choreograph idle circle → menu → general surface → selected domain → subcomponent → existing routed workspace. Keep a recognizable circle in every layer, smaller and calmer during focused work. Use one sidebar/breadcrumb/back model and the catalog role color/icon grammar. Keep every existing route, anchor and keyboard path available; map unavailable catalog examples to existing owners instead of making fake pages.

**Repository integration:** `PhengosHome`, navigation model/components, `App.tsx`, route shells and `phengos.css`. Reuse current route definitions and section anchors. The rendered intro remains a video; shell motion uses transform/opacity via installed Motion.

**Acceptance:** A PC user can enter from the film, select Home → Shopping and another domain/subcomponent, work in the existing page, go Back/Home without replay or lost drafts, and return to the circle. All 21 destinations still resolve. Keyboard focus, Escape and history behave predictably. Record the whole transition sequence, including circle behavior, depth changes and settled reading states; compare its desktop frames with catalog sheets 2–4, 8 and 10 before advancing.

### 2. Build one trustworthy static-plus-adaptive card system

**Scope:** Define typed card presentation, priority and action metadata shared by the general surface and domain views. Separate stable at-a-glance cards from contextual cards that appear only when their source is relevant. Design urgency, time, pin, user-selected plan and current-activity states; avoid duplicate visual emphasis. Cover today's plan, meetings, shopping, selected meal, training, near-term fixtures and pending reviews/proposals. Design source/freshness, empty/loading/error, compact and expanded states. Build a development-only scenario gallery for each catalog example so density, imagery, asymmetry and motion can be reviewed independently of backend availability.

**Repository integration:** Extend `phengosCardProjection.ts` and `PhengosContextCards.tsx`, introduce reusable frontend card primitives and typed view models, and connect existing API queries where available. Scenario fixtures live only in tests/development previews. Coordinate the view-model shape with the separate backend session; do not create new card endpoints or domain mutations here.

**Acceptance:** The development gallery displays premium, polished scenarios for a match within two days, today's gym block, a friend meeting, daily items, shopping, a chosen food and an agent proposal. The dashboard clearly explains today's priorities through card size, placement, imagery, source and action; it does not look like an even grid of interchangeable widgets. The normal home uses real sources when available and shows honest empty states otherwise. Pin/dismiss, source changes and card sizes behave predictably. Verify with focused tests, PC screenshots at representative widths and a changing-day walkthrough. Catalog sheets 3, 5–6 and 9 are the visual/behavior reference.

### 3. Complete card actions and assistant conversation as one workflow

**Scope:** Make card interactions understandable and useful. Standardize preview → inspect/adjust → explicit approve or decline → result → card update/history as frontend states. Bring existing assistant messages, streamed work logs, quick capture, plan proposals and review queue into the same card vocabulary. A card created in a conversation opens that exact saved thread. Keep state labels tied to real requests/results where connected; use labeled development scenarios for still-unavailable results. Redesign PC chat to coexist with the circle and cards, including focused reading, argument review and follow-up editing.

**Repository integration:** Extend current AssistantPage, proposal/conversation view models, existing frontend APIs and Query keys. The current pending-proposal feed and thread linkage are starting points. Preserve the existing server approval path where connected. Define an adapter-shaped proposal view contract so the separate backend work and a future voice transport can supply the same UI; do not implement backend card services or voice mode in this task.

**Acceptance:** The PC gallery and existing connected flows show a proposal in chat and its home card, review/adjust/approve/decline presentation, truthful pending/saved/stale/error states, and thread navigation. A user can tell what the assistant proposes, what will change, and where to continue the conversation without decoding implementation terms. Frontend tests cover state transitions; connected journeys use the already available endpoints. A backend integration gap is shown honestly rather than disguised as success. Catalog sheets 6–7 inform the flow; sheet 7's microphone/listening/speaking states remain excluded.

### 4. Migrate existing domains into layered card workspaces without feature loss

**Scope:** Apply the new shell, card hierarchy and role language to the real Home/Kitchen, Fitness, Calendar, Life, Learning, Finance, Social, Movies, Notebook, Self and Settings surfaces. Undercomponents become clear domain sublayers; deep work views keep their full forms, tables, editing and historical data. Prioritize everyday journeys (shopping/meal, training, calendar/meeting, assistant/review) before less-used domains. Preserve the existing feature inventory as a checklist; do not delete controls just to match a screenshot. Use consistent card header, action placement, status feedback and route transitions.

**Repository integration:** Migrate the existing routed feature components in bounded slices, reusing their APIs and mutation hooks. Extract shared visual primitives only after two real domains prove the pattern. Avoid a second router, state store, backend service or generalized widget engine.

**Acceptance:** Each migrated route has a catalog-consistent overview, sublayer and working view while its previously implemented actions still work. For the milestone boundary, walk the inventory's 21 destinations and run targeted journeys for shopping, Fitness, Calendar, assistant, Finance import and settings. Each journey must make its next useful action obvious and keep the surrounding dashboard context understandable. Desktop screenshots and motion recordings demonstrate one coherent system across routes rather than a styled landing page leading to the old app. Catalog sheets 4, 8 and 10 anchor the hierarchy.

### 5. Reach and measure premium visual, motion and accessibility quality

**Scope:** Refine art and interaction after the above flows are real. Match the catalog's quiet deep-blue starfield, disciplined glow, readable typography, spacing, asymmetry, role accents and restrained red urgency. Replace coarse cloud artifacts in every plate/film used by the app. Use purposeful spring/connector/settling motion from circle to card and back, with calm states during work. Respect reduced motion, keyboard, focus visibility and contrast. Profile the target PC: film decode, card interaction, scrolling, JS bundle and network refresh. Optimize the actual bottleneck rather than adding a full-scene renderer.

**Repository integration:** v17 Blender assets and authoring scene, CSS/Motion, existing Vite bundle, accessibility tests and browser instrumentation. [Apple's glanceable widget guidance](https://developer.apple.com/design/human-interface-guidelines/widgets), [motion guidance](https://developer.apple.com/design/human-interface-guidelines/motion), [W3C reduced-motion guidance](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions) and [WAI-ARIA dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) are quality checks, not new runtime dependencies. Evaluate Radix Dialog only if the evolving shell outgrows its current focus management.

**Acceptance:** Compare a documented set of PC reference frames and interaction recordings with all applicable catalog sheets; review with the user at each major visual gate. Verify film/poster/rest continuity, no pixelated blue clouds, no false loading/thinking states, visible keyboard focus and equivalent reduced-motion paths. Measure browser frame cadence/dropped frames on the target PC during intro, menu and cards before claiming the 60 FPS goal. No main-surface WebGL or per-frame React rerender. A production build and full preservation smoke test pass before release.

## Sequence and quality bar

Tasks 1–3 establish the frontend flow and can share design primitives, but complete them in that order with a reviewable PC walkthrough after each. Task 4 migrates domains in small verified slices. Task 5 is the measured acceptance pass; its motion, visual, accessibility and performance standards apply from Task 1 onward. Every review must show both still frames and interaction, including contextual data and meaningful actions. The current local preview remains an iteration for review. Public deployment requires a hosting target; this repository currently has no Git remote or hosting configuration. Do not call a visual milestone accepted until the user sees and accepts its actual desktop behavior.
