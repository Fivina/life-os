# Life OS v1.8B: Leisure and Movies

## Boundaries

Leisure is intentional life activity, not productivity debt. A movie trajectory describes a comfortable weekly range and reports `BELOW_RANGE`, `IN_RANGE`, or `ABOVE_RANGE`; being below the range does not create backlog, pressure, a Task, a Commitment, or a PlanBlock.

`Movie` is provider-neutral canonical metadata. External identity lives in `MovieExternalId`. `MovieWatchlistItem` represents intent, while `MovieViewing` represents an observed watch and preserves rewatches as separate rows. Selecting a recommendation is not evidence that the movie was watched.

Movie recommendations reuse the generic `Recommendation`, `RecommendationOption`, and `RecommendationOutcome` models. Candidate filtering is deterministic; scoring factors are stored with each option. Repeated accepted outcomes can flow through the existing thresholded Personal Learning job. One outcome never becomes a permanent preference fact.

## Providers

`MovieMetadataProvider` is the metadata boundary. The optional TMDB adapter uses official search/details endpoints when `MOVIE_METADATA_PROVIDER=tmdb` and `TMDB_API_TOKEN` is configured. Missing credentials return an empty search result and do not prevent startup or manual movie use.

Letterboxd direct API access is intentionally not implemented. Letterboxd currently makes API access request-only and excludes private recommendation and LLM/GPT-related projects. v1.8B accepts user-provided Letterboxd CSV exports through a provider-neutral preview/confirm adapter instead. Raw files are not stored; normalized rows, hashes, source identity, and reconciliation status are retained. Ambiguous rows remain `REVIEW_REQUIRED` until the user links them to a canonical movie.

`ShowtimeProvider` is a provider-neutral contract. v1.8B includes a bounded manual/fake path because no stable provider has been configured. Only city/region context is accepted; precise location history is not required.

## Prospective Flow

“I want to see X when it releases” creates a canonical movie reference and an existing `ProspectiveThread` with intent `WATCH_WHEN_AVAILABLE`. A dated movie uses `DATE_APPROACHING`; an undated movie waits for an explicit `EVENT_AVAILABLE` observation.

The flow is:

```text
release relevance
-> prospective eligibility
-> optional showtime options
-> planner-owned overlap feasibility
-> AttentionManager
-> SILENT / SHOW_PASSIVELY / MENTION_WHEN_NATURAL
```

A showtime is an option, never a Commitment. Conflicts with protected calendar state are reported as requiring a proposal path; v1.8B does not create a PlanBlock, alter a schedule, purchase a ticket, or book a seat.

## Lifecycle and Realtime

Movie, watchlist, viewing, import, trajectory, recommendation, prospective-thread, and attention mutations use the existing Event, Outbox, and WorldRevision infrastructure. Realtime messages only invalidate client query caches; clients refetch canonical state.

The due-thread worker is bounded and adaptive: dormant releases are checked sparsely, eligible windows daily, and AttentionItems are deduplicated by thread and reason.
