# Life OS v1.8C: Social Trajectory And Life Opportunities

## Boundaries

- `SocialTrajectory` is a configurable activity target, not a diagnosis or productivity debt.
- `Opportunity` is discovered external context, not a `Commitment`, `PlanBlock`, booking, or proof of availability.
- `SELECTED` records interest. Only explicit `EXECUTED` evidence records attendance and a qualifying `SocialActivity`.
- Finance exposes only `SocialBudgetSignal`; opportunity code never receives transactions, accounts, or merchants.
- Planner feasibility is read-only. Flexible study conflicts may be marked proposal-eligible only after strategic safety checks; the current plan stays unchanged until an existing `PlanProposal` is explicitly accepted.
- Attention decides whether an opportunity is silent, passive, or a natural mention. It does not notify, book, buy, reserve, pay, schedule, or contact another person.

## Pipeline

```text
OpportunitySource
  -> bounded fetch
  -> typed normalization
  -> stable provider identity / conservative cross-source dedupe
  -> hard filters
  -> ProspectiveThread, OpenThread, trajectory, recent activity, and learned-pattern matching
  -> optional DecisionGateway judgment for ambiguous survivors only
  -> Planner feasibility and strategic safety
  -> AttentionManager
  -> SILENT / Recommendation / proposal-eligible result
```

Named factors stay inspectable. Hard rules always outrank provider output. Exact provider IDs are strongest; cross-source reconciliation requires exact canonical title, start instant, and venue. The same artist on a different date remains a separate opportunity.

## Trajectory

The existing `Goal` and `Trajectory` tables hold the target and policy metadata. A weekly target stores `enabled`, `target_min`, `target_max`, and `week_starts_on`. The default can represent two meaningful activities per week but is user-configurable and can be disabled. Period state is deterministic: `BELOW_RANGE`, `IN_RANGE`, `ABOVE_RANGE`, or `DISABLED`. Language remains neutral.

Qualifying evidence is an explicitly logged meaningful `SocialActivity` or an attended opportunity outcome. Chat text and selecting an event do not count as attendance.

## Sources

`OpportunitySource` is provider-neutral and has deterministic fake-source coverage. The real adapter uses Ticketmaster Discovery API v2 event search with server-side API-key authentication, city/country/date/category parameters, bounded result size, and a configurable horizon. The official documentation checked for this implementation states a default quota of 5,000 calls/day, 5 requests/second, and deep paging limited to the 1,000th item. Life OS uses at most 100 results per configured run and does not call commerce endpoints.

Missing credentials produce an unconfigured source state and never prevent startup. Source failure preserves existing canonical opportunities and allows other sources to complete. External requests contain only city/region, country, date range, category, and result bound.

## Lifecycle And Outcomes

Opportunities use `ACTIVE`, `ENDED`, `CANCELLED`, `STALE`, and `ARCHIVED`. Historical rows are retained for outcomes. User state is separate: `AVAILABLE`, `INTERESTED`, `DISMISSED`, and `ATTENDED`.

Generic `Recommendation`, `RecommendationOption`, and `RecommendationOutcome` remain the recommendation contract. Outcome evidence is contextual and enters the existing bounded learning job; one rejection never creates a global category ban. Explicit attendance can resolve linked ProspectiveThreads.

## Events And Realtime

Lifecycle events include `social.trajectory_changed`, `social.activity_recorded`, `opportunity.discovered`, `opportunity.updated`, `opportunity.ended`, `opportunity.recommendation_created`, and `opportunity.outcome_recorded`. They advance `WorldRevision` and use the shared realtime invalidation path for opportunities, recommendations, sources, trajectory, and activities.

## Non-Event Suggestions

The bounded candidate contract represents `CALL_FRIEND`, `MESSAGE_FRIEND`, `CASUAL_DRINK`, `DINNER_WITH_FRIEND`, and `WALK_WITH_FRIEND`. Candidates require explicit context/reference evidence and always have `executable=false`; no messaging, calling, contact sync, reservation, or social graph is implemented.
