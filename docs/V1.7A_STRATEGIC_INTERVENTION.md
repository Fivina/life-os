# Life OS v1.7A Strategic Monitor and Plan Proposals

## Authority boundary

The v1.7A flow is:

```text
Learning and Planner canonical state
  -> StrategicMonitor
  -> ExamTrajectorySnapshot
  -> StrategicDeviation
  -> InterventionEngine
  -> optional DecisionGateway judgment
  -> Planner dry-run simulation
  -> PlanProposal
  -> explicit Apply / Modify / Reject
```

`StrategicMonitor` is not a planner. It reads canonical exams, study requirements, quality-adjusted sessions, current plan allocations, and planning debt. It never creates a `PlanBlock` or activates a plan.

`InterventionEngine` is not a calendar writer. It maps deterministic evidence into authority levels and the existing `AttentionAction` contract. Provider confidence is recorded as one confidence component and never grants write authority.

`PlanProposal` is not the current plan. Its candidate plan is an immutable, non-active snapshot produced by Planner V2. Creating or presenting a proposal changes no current `PlanBlock`.

## Strategic calculations

Calculation semantics are versioned as `trajectory-calculation-v1`.

Direct deterministic inputs:

- exam deadline from `learning_exams`;
- workload from explicit study requirements, with canonical exam targets as a declared fallback;
- effective completion from quality-adjusted study sessions;
- current scheduled study from active current plans and exam-linked actions;
- recent effective pace over a bounded 14-day window;
- broad future capacity from the existing Learning capacity calculation;
- currently allocated flexible time from current plan blocks;
- open planning debt linked to exam actions.

Derived values:

- remaining workload = total workload - effective completion;
- required weekly pace = remaining workload / remaining days * 7;
- actual weekly pace = recent effective minutes / 14 * 7;
- available additional capacity = broad capacity - all current flexible allocation;
- projected shortfall = remaining workload - target-exam allocation - additional capacity;
- buffer = target-exam allocation + additional capacity - remaining workload.

Missing deadlines or workload remain unavailable. Missing observations do not become zero-quality or psychological interpretations. Completeness is explicit as `COMPLETE`, `PARTIAL`, or `INSUFFICIENT`.

## Intervention policy

The versioned host policy uses the frozen authority levels:

```text
0 OBSERVE
1 SILENT_REPAIR_WITHIN_RULES
2 PREPARE_PROPOSAL
3 ASK_OR_DISCUSS_TRADEOFF
4 URGENT_ATTENTION
```

Minor or weak evidence remains `SILENT`. Moderate recoverable drift is deferred with `MENTION_WHEN_NATURAL`. High material drift can use `PROPOSE`. Critical ambiguous trade-offs use `ASK`; only measurable imminent and unrecoverable cases can reach `INTERRUPT`.

The versioned `strategy.intervention_needed` DecisionQuestion can add a bounded judgment and a CognitiveTrace. The deterministic host policy remains authoritative, and provider failure leaves the deterministic path intact.

## Planner simulation and application

Planner simulation reuses `PlanningContext`, existing candidates, constraints, personal-model inputs, hard commitments, freeze rules, and `CorePlannerV03`. A bounded target-exam recovery input is added to the candidate set. The simulation writes no `Plan`, `PlanBlock`, normal plan-applied event, or current-plan status.

Protected, user-locked, user-modified, fixed, and explicitly protected blocks are carried into the simulation and verified by stable signatures. A candidate that changes one is rejected.

Acceptance revalidates:

- proposal status and expiry;
- exact current plan identity and version;
- exam and study-requirement versions/content;
- protected block signatures.

Only `app.planning.strategy.apply_strategy_candidate` publishes the accepted candidate. It supersedes the old current plan, creates the new current plan atomically, and emits `plan.proposal_applied`.

## Proposal lifecycle

`plan_proposals` stores the exact source plan/version, frozen trajectory and deviation evidence, candidate plan, structured changes, measurable expected effects, trade-offs, confidence components, versions, and expiry.

Lifecycle:

- `DRAFT`: generated but not yet explicitly surfaced;
- `PRESENTED`: structured proposal shown for review;
- `ACCEPTED`: revalidated and applied by Planner;
- `MODIFIED`: original remains immutable and a child proposal is re-simulated;
- `REJECTED`: current plan remains unchanged and equivalent regeneration is cooled down;
- `EXPIRED`: stale advice cannot be applied;
- `APPLY_FAILED`: reserved for explicit technical failure handling.

Stable fingerprints suppress equivalent proposals. Material trajectory or plan changes produce a new identity. Rejection cooldown is contextual and does not become a universal preference.

## Learning, trace, and attention

Accept, Modify, and Reject create contextual rows in the existing `personal_training_examples` evidence table with `label_source=plan_proposal`. They explicitly state that one choice does not imply a universal preference.

When DecisionGateway is enabled, the CognitiveTrace records the trajectory snapshot, deviation, calculation version, provider route, and result. Proposal outcomes add a DecisionAudit linked to the same trace. No hidden reasoning is stored.

Proposal creation and presentation remain separate. Surfaceable proposals use the existing AttentionItem queue; v1.7A adds no notification or realtime transport.

## Example

An Algorithms exam has 600 effective minutes remaining, 30 minutes in the current plan, and recent pace below the required pace. The monitor emits an underallocation/pace deviation. Planner simulation increases Algorithms allocation while preserving a locked workout and exposes any reduction to a later exam as an explicit buffer trade-off. The old plan stays current until Apply. Modify re-runs Planner with the new constraint. Reject records contextual evidence and leaves the plan untouched.
