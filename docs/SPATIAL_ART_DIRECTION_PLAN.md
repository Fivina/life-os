## A. Visual Contract And Reference Breakdown

Write a compact look-development contract before making more detailed meshes:

- Mood: quiet, vast, cinematic; purposeful light in near-black space.
- Camera: one oblique establishing angle, explicit framing and safe UI regions.
- Focal order: Self Core first, recognizable domain planets second, atmosphere
  third. Foreground silhouettes frame the system rather than obscure it.
- Palette: blue-white core, violet Calendar/Learning, warm Home, living green/
  ocean Life, machined cyan Fitness. Do not flood everything with one blue light.
- Contrast: readable surface detail on the lit side, convincing dark hemisphere,
  restrained edge light. No blanket emission or overexposed object bodies.
- Effects: light scattering has a source; bloom follows bright emitters rather
  than acting as a substitute for form. Labels remain crisp.

Deliverable: saved reference comparison and written visual rules. Gate: every
subsequent asset can be evaluated against the same contract.

## B. Whole-Frame Blockout And Camera

- Establish scale hierarchy, asymmetric placement, useful negative space and
  three depth layers using simple forms before polishing every surface.
- Place foreground geometry on a distinct depth plane. Use occlusion and
  perspective, not merely additional rings on the same plane.
- Design system composition and a close-up view together; neither should rely
  on an object being tiny to hide a visual defect.
- Reserve space for future labels/navigation without constructing card layouts.
- Keep an authored desktop camera and a deliberate mobile composition; scaling
  the entire desktop image down is not an adequate mobile solution.

Deliverable: clean whole-frame blockout render and framing notes.
Gate: hierarchy and spatial depth read even with textures and bloom disabled.

## C. One Finished Look-Development Anchor

Finish Fitness/Orbit Barbell first as the shared quality benchmark, using the
existing editable pilot rather than throwing it away:

- Correct proportions and equatorial relationship between planet, shaft and
  plates; no impression of a separate dumbbell placed below a sphere.
- Machined bevels, collars, restrained luminous channels and contrasting metal
  roughness; enough detail to read at the intended screen size.
- Planet terrain with layered albedo/roughness/normal detail, not one generic
  color-noise shader. Atmosphere should preserve surface shadows.
- One consistent key/rim/fill rig, believable specular response and restrained
  bloom. Test a close-up and its actual system-scale appearance.

Deliverable: polished anchor close-up plus full-frame placement.
Gate: the same object reads as crafted and dimensional in both views. Reuse its
lighting/material principles, not its surface texture, across other domains.

## E. Scenery And Shared Lighting

- Author a restrained deep-space environment/backplate with purposeful placement
  of distant dust/galaxy detail. Bitmap assets are appropriate for far background;
  planets and interactive foreground remain real geometry.
- Replace obvious low-poly foreground placeholders with a small reusable family
  of detailed asteroid shapes. Instance them with varied silhouette and scale.
- Add foreground framing/occlusion and distant depth without covering controls.
- Apply one coherent light direction and color grade. Allow local warm/cool
  reflections, but do not let independently polished assets look pasted together.
- Judge the complete frame at full size and thumbnail size. Tune effects only
  after surfaces, silhouettes and shadow shapes are working.

Deliverable: complete cinematic static frame with all finished objects.
Gate: atmosphere supports focal hierarchy; the scene still works with UI hidden
and animation stopped. Record differences from the reference honestly.

## F. Preserve The Artwork In The Browser

- Bake/export the actual supported PBR channels, geometry and UVs to GLB.
  Implement atmospheric/emissive effects explicitly where glTF cannot retain
  the authored Blender shader. Keep procedural Blender sources editable.
- Keep root names/camera metadata stable; consolidate compatible geometry and
  bound texture resolution. Measure asset footprint and draw calls.
- Load the assets through the existing Three.js GLTFLoader in a development-only
  full-screen preview. Do not replace the production hub with an unfinished pass.
- Compare browser screenshots with the authored frame: color response, exposure,
  normals, missing maps, orbit visibility, silhouette and composition.
- Verify desktop/mobile framing, canvas pixels and loading/failure behavior.

Deliverable: runnable static browser artwork and saved comparison screenshots.
Gate: exported objects remain materially recognizable, the complete composition
is usable, and no new runtime errors or missing assets occur. The 60 FPS target
guides asset budgets; motion/performance acceptance is the next goal.

## Review Loop And Handoffs

For each chunk: inspect the reference -> name the concrete visual gap -> change
one relevant layer -> render at fixed framing -> compare -> record the outcome.
Do not call a result finished merely because it renders or a test passes.

Use milestone pauses for a compact handoff, not after every micro-edit. Save the
scene/source paths, screenshot paths, current accepted decisions and next steps.
Keep architecture, art direction, integration and final visual QA in the primary
session. Delegate only independent bounded work, such as preview scaffolding.

Recommended production split once camera/lighting decisions are stable: primary
owns the whole frame and acceptance; one worker owns a specific object source;
a second owns export/preview or a separate object with disjoint source files.
Review actual renders before integrating their work. More parallel interpretations
of the same scene are not a substitute for a shared artistic benchmark.

Navigation, warp effects, final moon/card mechanics and main-hub replacement are
later goals. Do not use animation to disguise unresolved artwork problems.
