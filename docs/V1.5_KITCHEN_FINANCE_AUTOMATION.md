# Life OS v1.5: Kitchen and Finance Automation

## Scope

Version 1.5 connects Kitchen, Chef, receipts, shopping, nutrition, Finance, media, and planning through typed domain services. It preserves the central authority rule: domains create canonical state and Actions; only the Core Planner creates PlanBlocks.

## Kitchen

- Canonical ingredient identities and aliases normalize receipt, recipe, shopping, and manual inventory names.
- Inventory remains lot-based. Mutations and meal completion use deterministic unit validation and earliest-expiry consumption.
- Fridge items can be marked as staples with explicit low-stock and refill targets. Manual `adjust` sets the counted quantity; `consume` subtracts from earliest-expiry lots.
- Receipt confirmation creates food lots only for accepted food lines. Household, deposit, and other lines remain Finance-only.
- Receipt upload validates base64, MIME signatures, size, user ownership, storage paths, and content hashes.
- Duplicate assets and repeated confirmation are idempotent.
- Provider failure leaves a receipt in `pending_vision`; it never partially mutates Inventory or Finance.

## Chef

Chef scoring is deterministic and explainable. It considers inventory availability, expiry, nutrition, recent repetition, explicit preference evidence, recommendation outcomes, shopping friction, time, cooking competency, and bounded grocery-budget context.

Recommendation sets persist generic Recommendation, Option, and Outcome records. A single rejection remains weak evidence and does not become a permanent preference. Selecting a meal creates a canonical MealPlan plus required shopping and cooking Actions. Cooking depends on shopping when ingredients are missing.

Meal completion consumes inventory, records nutrition and feedback, completes the cooking Action, emits outcomes, and updates bounded technique competency evidence. Only explicit strong preference language becomes a memory candidate.

## Shopping

- Selected meals create `required` needs, configured low-stock staples create `restock` needs, and unselected recommendations create `optional` needs.
- Canonical ingredient/unit pairs aggregate into one shopping-list row.
- Purchase checkoff can add one inventory lot and is idempotent.
- Later receipt confirmation reconciles the purchase instead of adding stock twice.
- Shopping Actions carry provenance and planner dependency metadata.

## Finance

- CSV imports are staged as drafts before canonical mutation.
- Header mapping, date parsing, debit/credit handling, comma decimals, malformed-row isolation, and content-hash deduplication are deterministic.
- Ambiguous categories require review. User category corrections become merchant rules for later imports.
- Transaction fingerprints prevent duplicates. Receipt and CSV records reconcile by date, amount, currency, and merchant.
- Amounts use `Decimal`/database numeric columns and retain currency.
- Monthly totals, category totals, budgets, likely recurring expenses, savings goals, and safe-to-spend are queryable.
- Safe-to-spend always returns its assumptions and never invents an account balance.
- There are no bank connections, payment operations, or money movement APIs.

## AI And Media

`VISION` and `IMAGE` are provider-neutral AI Gateway capabilities. Receipt extraction uses schema-constrained output. Optional generated media is content-addressed and cached. Core arithmetic, shopping aggregation, inventory consumption, budgets, recurring detection, and recommendation scoring require no AI.

## Assistant Boundaries

- `CHEF` receives bounded Kitchen state, relevant memory, Fitness nutrition, and only the grocery-budget bridge from Finance.
- `FINANCE_ADVISOR` receives monthly summaries, budgets, recurring expenses, savings trajectory, safe-to-spend, and at most eight recent transactions.
- The general assistant receives bounded spending capacity, not raw transaction history.
- Finance has no semantic-memory scope and raw transaction details are never written to memory.

## Planner Contract

Meal selection writes Actions, never PlanBlocks. The cooking Action contains `depends_on_action_id` when shopping is required. Planner placement treats an unresolved dependency as a hard violation and will not place cooking before the prerequisite shopping block.

## API Surfaces

- `/api/v1/kitchen/chef/recommendations`, `/meal-plans`, `/competencies`
- `/api/v1/kitchen/shopping-list`, `/shopping-items/{id}/purchase`
- `/api/v1/receipts`
- `/api/v1/media`
- `/api/v1/finance/overview`, `/transactions`, `/imports`, `/budgets`, `/recurring/refresh`
- `/api/v1/status`

## User Interface

Kitchen now includes receipt review, persisted Chef choices, recommendation rejection, planned meals, a step-by-step cooking view, serving controls, completion feedback, fridge consume/count controls, staple targets, grouped shopping checkoff, and competency progress. Explicit empty states cover a new fridge, Chef, planned meals, recipes, shopping, competencies, budgets, recurring expenses, and transactions. Finance includes safe-to-spend assumptions, CSV staging/review, budgets, recurring expenses, and recent transactions. The visual hub is unchanged.

## Deliberate Deferrals

Version 1.5 does not implement the final Self Core dashboard, universal Quick Capture, a global review queue, bank integrations, money movement, a final proactive recommendation policy, global notification redesign, or the v2.0 visual redesign.
