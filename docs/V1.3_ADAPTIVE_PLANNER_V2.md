# Life OS v1.3 Adaptive Planner V2

Source reviewed: the full v1.3 implementation prompt, sections 0-108, plus the Life OS 2.x implementation handbook. This report records the implemented boundary after repository audit, migration, regression testing, and PostgreSQL verification.

## 1. Current planner architecture found

The repository already had one deterministic planning authority: canonical Actions and Commitments feed `app.planning`, which owns Plans and PlanBlocks. V0.4 supplied execution and replanning, domain services supplied planner candidates, V0.9 supplied bounded Personal Learning parameters, v1.2 supplied semantic memory, and the Worker supplied scheduled background execution. V1.3 extends those systems rather than introducing a second scheduler.

## 2. Schema changes

Migration `0014_adaptive_planner_v2` adds candidate-group and variant metadata to Actions; strength, provenance, scope, windows, and penalties to Constraints; overload state to Plans; stability, variant, original placement, and residual fields to PlanBlocks; and new `planning_allocations` and `planning_debts` tables. The migration is additive, has defaults for existing rows, foreign keys, user scoping, unique keys, and lookup indexes.

## 3. Action variant model

Learning's full, standard, reduced, minimum, and activation choices and Fitness's full, reduced, and minimum choices share a stable candidate group. The daily planner selects at most one member. State-based eligibility prevents a technically available but behaviorally unrealistic large variant from winning on low-state days. Activation is available only for low-state, late-day, low-completion, or debt recovery contexts.

## 4. Slot scoring

Planner V2 generates slots at configurable granularity and scores each feasible candidate, variant, and slot. Factors include canonical priority, trajectory value, urgency, neglect, stress, activation, capacity fit, Personal Learning completion/routine fit, hard/soft constraints, duration fit, adjacency, fragmentation, context switches, location/context compatibility, and energy-time fit. Tie-breaking is deterministic.

## 5. Personal Learning integration

Completion and routine lookups are keyed to the future slot, not plan-generation time. Learned ranking remains bounded, capacity remains clamped, low confidence scales influence down, and corrected or invalidated evidence is excluded. Terminal partial/cancel outcomes and manual move metadata now feed feature extraction without mixing future labels into planning features.

## 6. Constraint system

Canonical Constraints remain authoritative. The resolver can translate only pinned, active/confirmed scheduling memories through a controlled typed interface. Hard constraints reject placements. Soft preferences contribute explainable penalties or bonuses. Irrelevant memory is ignored, provenance is retained, and current canonical commitments always win.

## 7. Rolling planner

The rolling allocator produces user-scoped allocations over a configurable ten-day horizon. It accounts for hard commitments, grouped remaining work, deadlines, priority, capacity, open debt, and prior completion. It reports feasible, tight, or impossible-before-deadline status and persists explicit shortfall instead of silently compressing work.

## 8. Daily planner

The daily layer consumes today's allocations, current state, fixed commitments, typed constraints, candidate variants, Personal Learning snapshot, and preserved prior blocks. It creates PlanBlocks only through the central planner and retains explicit slack. Plan responses expose structured unscheduled risk and overload details.

## 9. Replan and debt

Partial completion records actual work and residual debt. Skip, miss, and placement cancellation preserve the underlying requirement as debt; they do not clone Actions. Completion resolves debt and closes mutually exclusive siblings when appropriate. Missed work can trigger a remaining-day replan whose horizon starts at the current time, preventing placement in the past.

## 10. Overload

Plans store overload status, required, available, scheduled, and shortfall minutes. The planner protects hard commitments first, chooses smaller valid variants, defers lower-priority flexible work, retains unscheduled items, and emits `planning.overload.detected`. The Calendar surfaces overload and Needs Attention instead of presenting an impossible plan as feasible.

## 11. Plan stability

Replans preserve terminal history, in-progress work, the configurable freeze window, manual moves, and user locks. Move commands validate overlap, preserve original placement, and mark the new block as user-directed evidence. Plan lineage, reason, diff, previous plan, and replan timestamp remain queryable.

## 12. Morning automation

`MorningPlanner` is user/date scoped and idempotent. The Worker invokes it only after `PLANNER_MORNING_HOUR` in the configured timezone. The current-plan API provides an idempotent first-access fallback, so a missed worker cycle cannot leave the Calendar empty.

## 13. Frontend changes

The existing Calendar was evolved without a redesign. It now handles first-access plan loading, presents a ten-day Week Map, shows overload and unscheduled risk, supports Replan, Complete, Partial, Skip, and deterministic Why Here controls, and labels execution variants and stability state.

## 14. AI usage

AI has no scheduling authority and is not required by the planning path. It may interpret or explain intent through existing bounded assistant infrastructure. Final slots, variants, feasibility, constraints, debt, overload, and PlanBlocks are deterministic application logic. Planner-specific assistant tools expose horizon and overload state but cannot bypass planner services.

- Frontend suite: 49 tests across 9 files pass.
- TypeScript and Vite production build: pass.
- Python compile check: pass.

The v1.3 suite covers mutual exclusion; full, reduced, minimum, and activation selection; future-slot scoring; confidence bounds; corrected patterns; hard and soft memory constraints; irrelevant-memory filtering; rolling shortfall; partial debt and allocation progress; manual-move stability; morning schedule/idempotency; and operation with AI disabled.

## 16. Known limitations

- Placement optimization is bounded deterministic greedy selection with local schedule validation; it is not a general-purpose mixed-integer solver.
- Natural-language memory translation intentionally recognizes a small scheduling grammar. Ambiguous preferences remain advisory until converted to a typed planning preference.
- Location and energy requirement support is foundational: factors and contracts exist, while external travel-time and sensor integrations remain out of scope.
- The morning worker uses the existing polling worker rather than an external cron service.
- SQLite tests cannot preserve timezone offsets exactly; production PostgreSQL uses timezone-aware columns and all planning boundaries require aware input.

## 17. V1.4 readiness

V1.3 leaves stable interfaces for richer manual low-energy commands, improved local search/backtracking, more typed preference interpreters, notification policies, and deeper recommendation outcome bridges. No v1.4 Fitness Coach, v1.5 Learning Tutor, or v2.0 multi-agent system was implemented.
