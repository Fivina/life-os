# v1.6D Laya/Jev Provider Routing

## Boundary

`DecisionGateway` remains the only application boundary for bounded typed decisions. `LayaLocalProvider`, `JevProvider`, and `FakeDecisionProvider` receive only a validated `DecisionQuestion` and bounded `DecisionContext`; they receive no database session, domain service, tool registry, or Planner handle. Provider confidence is evidence, never permission or canonical authority.

The separate generative `AIGateway` and Gemini escalation path are unchanged. No v1.6D provider can write `PlanBlock`, inventory, memory, finance, notifications, or any other canonical state.

## Verified Upstream Contracts

Contracts were checked on 2026-09-25.

- Laya upstream: `NandhaKishorM/laya`, current README release line `0.3.20`. The adapter uses the documented lazy `Router()` plus `Router.predict(state, questions, model=...)` contract. Choice, score, and noul questions are evaluated in one call; model weights use the upstream Hugging Face cache, optionally rooted through `LAYA_CACHE_PATH`/`HF_HOME`. Laya is imported only on first enabled inference. Source: <https://github.com/NandhaKishorM/laya>
- TypeSafe's Jev API: `POST https://api.typesafe.ai/v1/systemone`, Bearer authentication, model `jev-latest`, and a question map keyed by caller IDs. The authenticated `GET /v1/models` endpoint lists account-available model names. Life OS uses a pooled `httpx.Client` because the verified HTTP contract is small and no additional SDK is required. Source: <https://api.typesafe.ai/docs>
- Life OS records provider-reported token and monetary metadata when present; it does not invent a token price or convert USD to EUR without an authoritative rate.

Real-provider smoke tests are opt-in. Ordinary tests mock both runtime boundaries and never download Laya checkpoints or call Jev.

Install the optional local runtime only on hosts intended to run it:

```bash
python -m pip install -r backend/requirements-laya.txt
```

## Routing

The versioned `DecisionRoutingPolicy` supports `FAKE`, `LAYA_ONLY`, `JEV_ONLY`, `AUTO`, and `SHADOW`.

`AUTO` prefers Jev for every question/context it supports. Laya remains the local fallback when Jev fails or returns below the configured confidence threshold; if Jev cannot support a question, Laya may serve it directly. Laya is not removed and remains independently switchable. If no valid provider remains, the decision fails explicitly so the existing cognitive cycle can apply its safe `SILENT` degraded behavior.

Routing never inspects arbitrary user-prose keywords. Manual provider override is accepted only outside production and is traced with a reason code. Initial confidence thresholds are conservative placeholders pending measured, reviewed benchmark evidence.

## Shadow And Evidence

Shadow sampling is deterministic over policy version, event ID, and question ID/version. It is restricted by configured families, sample rate, external-provider enablement, a daily shadow budget, and the general Jev daily budget. A shadow answer never changes the operational result, even when it disagrees or fails.

`decision_provider_usage` records provider/model, role, question count, routing reason, status/error, token units, latency, request ID, and reported EUR cost. `decision_disagreements` links the trace, stable bounded-context hash, question/version, both provider answers/probabilities/confidences, comparison role, operational result, policy version, and an optional later `DecisionAudit`. Disagreements start unreviewed and are never automatic truth or training labels. `DecisionTrainingExample.decision_disagreement_id` is optional and is populated only by a later evidence workflow.

Jev is an external service. Only bounded facts and explicit references selected by `DecisionContextBuilder` are sent. Full conversations, memory collections, financial history, kitchen inventory, goals, and unrelated life state are excluded. Jev credentials are fetched from Supabase Vault for the current authenticated user into a request-scoped adapter; process-level Jev keys are not used for account decisions. The key is absent from health output, traces, usage rows, logs, benchmark artifacts, and frontend configuration.

## Benchmark

The synthetic `life-os-decisions-v1` dataset has 21 cases, three each for attention, curiosity, context relevance, prospective relevance, memory relevance, contributor activation, and ordered urgency scoring. It contains no personal user content. Reports retain case/version/label provenance and expose sample count, valid-output, exact and acceptable match, score error/tolerance, failure/unsupported rates, median/p95 latency, cold versus warm latency, Brier score, log loss, expected calibration error, and reported external cost.

The report has no single composite winner. It creates a `candidate` task-family routing profile only when at least three valid cases support a family. It never edits production configuration or activates itself. Strong explicit v1.6C examples can be selected later through `FeedbackBenchmarkSelector`; weak, skipped, model-disagreement, incomplete, or contradictory evidence is excluded. Benchmark cases are evaluation data and no training or checkpoint mutation exists.

Run the deterministic offline report from the repository root:

```bash
backend/.venv/Scripts/python.exe scripts/run_decision_benchmark.py
```

The generated private/runtime report is written under `.cache/benchmarks` and is excluded from source packaging.

## Configuration

Fresh environments remain offline and safe: the master decision switch is off, routing preference is `AUTO` (Jev-first), Jev has no account credential until one is added to Vault, Laya and shadowing are disabled, and no provider request occurs. Configuring `AUTO` does not activate the dormant decision infrastructure. `backend/.env.example` documents these switches. When shadowing is deliberately enabled, Laya is the default comparison provider and has no operational authority. `/api/v1/decision/providers` is authenticated and reports enabled, available, loaded, model/version, last error, and last success without pinging Jev or exposing credentials.

Migration `0029_jev_vault_provider` extends the provider-secret functions from `0028_provider_secrets_vault` to accept Jev. Apply both only after the Supabase Vault/security setup is verified. The Settings page enables Jev key entry only when the database reports that Jev's allowlist migration is installed.
